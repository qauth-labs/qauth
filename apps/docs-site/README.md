# docs-site

The QAuth documentation site (Astro + Starlight), published at
[docs.qauth.dev](https://docs.qauth.dev). Source lives here; deployment is
handled by Netlify's own git-based continuous deployment, configured in
`netlify.toml` at the repo root.

## Local development

```bash
pnpm install
pnpm exec nx dev docs-site
```

Starts the Astro dev server with HMR. `pnpm exec nx typecheck docs-site` runs
`astro check` over `.astro`/`.mdx` content; `pnpm exec nx test docs-site` runs
this project's drift-check invariants (see below).

## Build

```bash
pnpm exec nx build docs-site
```

Output lands at `dist/apps/docs-site` (redirected there by `astro.config.mjs`'s
`outDir`, so it matches the `build` target's declared Nx output). This is a
static site — `astro build` alone is enough to produce everything that gets
deployed; there is no separate asset pipeline.

`public/openapi.json` is copied verbatim to `dist/apps/docs-site/openapi.json`
by Astro's build (anything under `public/` publishes at the site root
unchanged). It is a **committed, static snapshot**, generated by
`pnpm exec nx run auth-server:openapi-export`, not something this build
regenerates. Changing an `auth-server` route does not change this site's
build output — re-run that export and commit the result to pick up the
change.

## What actually feeds the build

Beyond this directory, the build also reads, **in place**, two directories
outside `apps/docs-site`:

- `docs/adr/*.md`
- `docs/security/*.md`

`src/content.config.ts`'s `records` collection loads them via a `glob()`
loader and renders them at `/reference/records/**`; `src/lib/records.ts`
reads the same two directories a second time (directly off disk) to build
that section's index page. Editing an ADR or the security review changes the
published site without touching anything under `apps/docs-site/` — the
deploy workflow's path filter accounts for this (see below); a filter of
`apps/docs-site/**` alone would not.

## Guarded by drift checks

`pnpm exec nx test docs-site` runs four invariants
(`src/invariants/*.ts`) that fail the build on: broken `path:line` anchors,
missing OpenAPI endpoint coverage, unresolvable internal links, and
undated/false status claims. The deploy workflow runs this before building,
so a guard failure blocks the deploy — it does not publish a broken site.

## Deployment

Netlify's own git-connected build, configured by `netlify.toml` at the repo
root. Netlify clones the repository, installs the pnpm workspace, runs
`pnpm exec nx build docs-site`, and publishes `dist/apps/docs-site`. Pushes to
`main` produce a production deploy and pull requests produce a deploy preview,
both on Netlify's side — no repository secrets and no GitHub Actions step are
involved.

There used to be one: `.github/workflows/docs.yml` built the site in Actions and
uploaded the prebuilt output through the Netlify CLI, which needed a
`NETLIFY_AUTH_TOKEN` and a `NETLIFY_SITE_ID`. It was removed in favour of
Netlify's own CD. The site's checks did not go with it — `ci.yml` runs
`nx affected -t lint typecheck test build`, which covers `docs-site` (its drift
invariants included) whenever the diff touches it or anything it reads.

Two settings in `netlify.toml` are load-bearing, and both are documented at the
lines that set them:

- **`PNPM_VERSION`.** The root `package.json` declares
  `engines.pnpm: ">=11.0.0"` but pins the exact version only inside each
  workflow's `pnpm/action-setup` input, so an external builder has nothing to
  read it from. Unset, Netlify activates its bundled pnpm and the install fails
  with `ERR_PNPM_UNSUPPORTED_ENGINE` before anything is built. Keep it in step
  with `.github/workflows/*.yml`.
- **`publish`.** `dist/apps/docs-site`, not `apps/docs-site/dist` — see
  [Build](#build) for why `outDir` points at the workspace root. A publish path
  aimed at Astro's default location deploys an empty directory and reports
  success.

Because `netlify.toml` overrides the equivalent fields in the Netlify UI, the
build is reproducible from the repository rather than from dashboard settings
nobody can review.

## DNS and TLS for docs.qauth.dev

1. In the Netlify site's **Domain management**, add `docs.qauth.dev` as a
   custom domain.
2. At the DNS provider for `qauth.dev`, add a **CNAME** record:
   `docs` → `<your-site-name>.netlify.app` (Netlify shows the exact target
   once the domain is added). `docs` is a subdomain, so a CNAME is enough —
   no apex/ALIAS record is needed.
3. Once that CNAME resolves, Netlify automatically provisions and renews a
   free TLS certificate (Let's Encrypt) for the domain — no certificate
   files to manage or rotate by hand. DNS propagation can take anywhere from
   minutes to a couple of hours before the certificate issues.

`astro.config.mjs`'s `site: 'https://docs.qauth.dev'` is what the build uses
to generate the sitemap and canonical URLs — it assumes this domain is live
over HTTPS.
